# 運用ルール（Claude Code × Codex × 利用者）

新しいチャットでも、利用者が何も説明しなくても同じ進め方になるようにする文書。
Claude Code は `CLAUDE.md` から、Codex は `AGENTS.md` から、ここに来る。目的・基準は `docs/PROJECT.md`、現在地は `docs/HANDOFF.md`。

## 1. 役割

| 担当 | やること | やらないこと |
|---|---|---|
| 利用者 | 目的・優先順位の判断、確定情報（連絡先・許認可・人名など）の提供、Codex への依頼文の貼り付けと結果の持ち帰り、公開の判断 | — |
| Claude Code（司令塔） | 設計・実装・検証・commit & push、Codex の指摘と提案の取捨選択、`docs/` の更新、次への引き継ぎ | 利用者の確定判断を代わりに行うこと、未確定情報の仮埋め、公開、master への直接 push |
| Codex（独立した目） | 監査（A）・分析と提案（C）。読み取り専用で、実装者とは別の視点で見る。必要なときだけ並行実装（B） | 作業ブランチ以外への push、依頼されていないコード変更 |

同じモデルが実装と確認を両方すると見落としが重なる。そのため確認は Codex に分ける。ただし毎回同じ重さでは無駄なので、下の段階を使う。

## 2. 進め方（フェーズ）

1. **目標・設計**: `docs/PROJECT.md` が埋まっているか確認する。大きな作業（新ページ・全体のデザイン見直し・新機能）の前に、変更方針を3〜5行で `docs/HANDOFF.md` の「進行中」に書く。目的に合わない案は実装前に落とす。
2. **骨格**: 構成・導線・ナビ・共通部品。
3. **内容**: 文章・料金・画像。未確定は「準備中」。
4. **磨き込み**: 色・フォント・CTA・余白。Codex の分析・提案（C）を一度入れて、Claude Code が取捨選択して実装する。
5. **公開前ゲート**: `PROJECT.md` の 7 のチェックを順に埋める。全体監査をかける。
6. **公開判断**: 利用者が決める。

後ろのフェーズに進んでから前のフェーズを大きく直すのは高くつく。迷ったら前のフェーズの文書を直してから進む。

## 3. Codex の使い分け（トークンを使う所を絞る）

| 段階 | 変更の例 | Codex |
|---|---|---|
| 0 | 誤字、文言の微修正、docs のみ、スクリーンショット追加 | 不要。テストのみ |
| 1 | 見た目・構成・新ページ・CTA・色・フォント・フォームの変更 | 監査（A）を依頼 |
| 2 | 公開方針に関わる変更（noindex、`SITE.PUBLISHED`、`config.ts`、許認可の表記、参考サイトの文章、`/privacy`） | 監査（A）を必ず依頼。観点を絞って渡す |
| ゲート | 公開前、または大きな区切り | 全体監査（A）。観点は AGENTS.md すべて |
| 見直し | デザイン・導線を大きく変える前 | 分析・提案（C）を1回 |

- 段階は Claude Code が判断し、依頼文に書く。迷ったら上の段階。
- 同じテーマの修正確認は前の Codex チャットに続けて貼る。テーマが変わる／長くなったら新しいチャット。
- 依頼文は短くする。手順・観点・出力形式は `AGENTS.md` にある。

## 4. 完了の定義（push してよい条件）

1. `npm run build` が成功、`npx astro check` が 0 errors、Playwright が全件成功。
2. 見た目を変えたら 1440px / 390px のスクリーンショットを `docs/review-screenshots/` に保存。
3. 新しい方針・不具合の修正にはテストを足した。
4. `CLAUDE.md` 1・2 に反していない。
5. 段階 1 以上なら、Codex 依頼文を出した（監査の結果が出るまで「マージ可」とは言わない）。

## 5. 毎回の終わりにやること（Claude Code）

1. `docs/HANDOFF.md` を更新（現在地・直近の判断・次にやること・利用者に確認が要ること）。判断は `docs/DECISIONS.md` に1行足す。
2. commit & push（作業ブランチ）。
3. 利用者に次の3つを出す。
   - Codex 用の依頼文（段階 1 以上のとき。段階 0 は「監査不要」と理由）。
   - 次の Claude Code に貼る文: 「`docs/HANDOFF.md` を読んで続きをお願いします。Codex の結果は添付画像のとおり。」の一言で足りるようにする（状況は HANDOFF.md に書いてあるため、長い説明を毎回書かない）。
   - 次に使うモデルと強度。
4. 利用者の確認が必要なこと（確定情報・判断）は、最後にまとめて短く聞く。

## 6. 新しいチャットを始めたとき（Claude Code）

1. `CLAUDE.md`（自動で読まれる）→ `docs/HANDOFF.md` →（必要なら）`docs/PROJECT.md`。`git log -5` と `git status` で HANDOFF と実際が合っているか確かめる。
2. 利用者が何も言わなくても、HANDOFF の「次にやること」から始める。画像（Codex の結果）が添付されていたら先に読む。
3. 方針や目的が HANDOFF・PROJECT で決まらないときだけ利用者に聞く。

## 7. トークンを節約するルール

- 毎回読まれるファイル（`CLAUDE.md` / `AGENTS.md`）は短く保つ。詳細は `docs/` に置き、必要なときだけ読む。
- 大きなファイルは範囲を指定して読む。直前に編集したファイルを読み直さない。ビルド結果は末尾だけ見る。
- スクリーンショットは変更したページだけ。全ページを毎回撮らない。
- Codex の指摘は、要点だけを抜いて Claude Code に渡す（画像1枚で足りる）。
- チャットが長くなったら、HANDOFF を更新して新しいチャットに切り替える。長い履歴を抱えたまま続けない。
- モデルの目安: 小さな修正・実装は Sonnet 5.5、設計・横断的な変更・Codex の提案の取捨選択は Opus 5.5。
- 強度（エフォート）の目安。ターミナル／デスクトップでは `/effort` で切り替える（`/effort auto` で保存値を解除、`s` キーでそのセッションだけ）。Sonnet 5.5 / Opus 5.5 の既定は medium。
  - low: 誤字・文言・docs・HANDOFF の更新など定型作業。
  - medium: 通常の実装、テスト追加、Codex の小さな指摘の修正。
  - high: 新ページ、CTA・色・フォントの見直し、導線の変更、Codex 提案の取捨選択。
  - xhigh: 公開前ゲート、設計の大きな見直し、原因が分からない不具合。
  - 1回だけ深く考えさせたいときは、依頼文に `ultrathink` と書く（その1ターンだけ強度が上がる）。
  - Claude Code は自分の強度を自動では切り替えられない。毎回の終わりに「次の作業の推奨強度」を出し、利用者が `/effort` で合わせる。

## 8. 文書の持ち主

| 文書 | 内容 | 更新する人 |
|---|---|---|
| `CLAUDE.md` | 毎回守る方針（安全・参考サイト・デザイン・検証）。短く保つ | Claude Code（方針の変更は利用者の確認後） |
| `AGENTS.md` | Codex の手順（A 監査・B 実装・C 提案） | Claude Code |
| `docs/PROJECT.md` | 目的・成果の定義・訪問者・ゲート | 利用者の判断を受けて Claude Code が更新 |
| `docs/WORKFLOW.md` | この文書 | Claude Code |
| `docs/HANDOFF.md` | 現在地と次にやること | Claude Code（毎回） |
| `docs/DECISIONS.md` | 決めたことと理由（1行ずつ） | Claude Code（毎回） |

## 9. Codex の呼び出し方（`codex` が使える環境：利用者のターミナル／デスクトップアプリ）

利用者の環境には `codex-cli`（0.154.0 で確認）が入っていて、ChatGPT のログインで動く。この環境の Claude Code は、依頼文を利用者に貼ってもらわず、**自分で Codex を呼んで結果を読む**。`codex` が使えない環境（クラウドのチャットなど）では、従来どおり依頼文を出して利用者が貼る（`CLAUDE.md` 5）。

### 呼び方（監査・提案とも読み取り専用）

依頼文は `CLAUDE.md` 5 の形で作り、`.codex-out/<テーマ>-prompt.txt` に保存して渡す。結果は `.codex-out/<テーマ>-result.md` に書かせる（`.codex-out/` は git に入れない）。

```
Get-Content -Raw .codex-out\<テーマ>-prompt.txt | codex exec -m gpt-5.6-sol -s read-only -C . -o .codex-out\<テーマ>-result.md -
```

- 実行は PowerShell の形。Git Bash なら `cat ... | codex exec -m gpt-5.6-sol -s read-only -C . -o ... -`。
- `-m gpt-5.6-sol` は毎回付ける。`~/.codex/config.toml` の既定モデル（gpt-6-sol）は ChatGPT アカウントでは使えず 400 エラーになるため（2026-10-10 に確認）。使えるモデルが変わったら `docs/HANDOFF.md` の環境欄と合わせて直す。
- `-s read-only`: 読み取り専用（コードを変更させない）。Codex を実装（B）で使うときだけ `-s workspace-write` とし、必ず `codex/<テーマ>` ブランチ上で行う。
- 同じテーマの修正確認は、前回の会話を続ける: `codex exec resume --last "<追加の依頼>"`。
- 監査は3分前後かかる。バックグラウンドで実行し、終わったら `-o` のファイルを読む。
- 認証は保存済みのログイン（ChatGPT のサブスク）を使う。**API キーは使わない**（環境変数 `OPENAI_API_KEY` / `CODEX_API_KEY` も設定しない）。クラウドのチャット環境に Codex を入れる方法は、API キーが要るため採用しない。サブスクの利用枠は Claude Code の監査・提案でも消費されるので、段階 0 では呼ばず、段階の基準（3）を守る。
- 読み取り専用の制限を信用しすぎない。実行の前後に `git status` で、作業ツリーが変わっていないことを確かめる。変わっていたら元に戻し、利用者に報告する。

### 初回の動作確認（最初の1回だけ。結果を `docs/HANDOFF.md` に書く）

0. 認証がサブスク（ChatGPT のログイン）か確かめる: `codex login status`（無ければ `codex --help` で確認）。API キーでのログインなら、利用者に伝えて `codex login` で ChatGPT のログインに切り替えてもらう。
1. `codex exec -s read-only "このリポジトリの README.md の1行目を答えてください。ファイルは変更しないでください。"` が動くか。
2. `-s read-only` がこの環境（Windows ネイティブ）で効くか（`git status` が変わらない）。
3. `-o` のファイルが作られ、日本語が文字化けしていないか。
4. 動かない場合は、利用者に貼ってもらう従来の方法に戻す。

### Codex の結果の扱い

- Claude Code は結果の要点（指摘・提案の一覧）を利用者に短く見せ、採用・保留・却下を理由つきで示す。結果が出る前に「マージ可」と言わない。
- 長い結果は全文を会話に貼らない。要点だけを `docs/HANDOFF.md` に残す。
- Codex の推論の強さは、Codex 側の設定（`~/.codex/config.toml`）の既定を使う。変える必要があれば利用者に聞く（指定の仕方は未確認）。

## 10. モデル・強度の切り替えとトークン（Claude Code / Codex）

### Claude Code（公式資料で確認済みの仕組み）

- **新しいチャットは、モデルを替えるたびには要らない。** モデルごとにキャッシュが別なので、`/model` で替えると次の1回だけ、会話の全履歴をキャッシュなしで読み直す（遅く、高い）。1回きりの追加費用で、その後は新しいモデルのキャッシュで安くなる。
- **キャッシュは、サブスクでは最後のやり取りから1時間で切れる。** 1時間以上あいたあとの切り替えは、もともとキャッシュが無いので追加費用がかからない（確認も出ない）。
- **強度（エフォート）の変更は、Sonnet 5.5 / Opus 5.5 ではキャッシュが保たれ、追加費用がない。** 作業の途中で自由に替えてよい。
- よって運用は次のとおり。
  1. **モデルは作業の区切り（タスクの切れ目、`/clear` の直後、1時間以上あいたあと）で替える。作業の途中では替えない。**
  2. **強度は、必要に応じて途中でも替えてよい**（目安は 7）。
  3. タスクが終わったら `docs/HANDOFF.md` を更新して `/clear`（費用ゼロ）。次のタスクを新しいモデル・強度で始める。文脈は HANDOFF で引き継ぐので、長いチャットを抱えずに済む。これが一番トークンの無駄が少ない。
- **Claude Code は自分のモデルを自動では切り替えられない。** 例外は `opusplan`（計画段階は Opus、実行段階は Sonnet）で、切り替えのたびにキャッシュが作り直しになるため標準にはしない。毎回の終わりに「次の推奨モデル・強度」を出し、利用者が `/model` `/effort` で合わせる。
- 一部の作業だけ別のモデルに任せたいときは、**サブエージェント**を使う。サブエージェントは自分の会話を持ち、定義に `model` を書ける。親の会話のキャッシュには影響しない。
- 大きな画像を溜めると、古い画像から落とされ、1回キャッシュが作り直しになる。スクリーンショットは必要なものだけ貼る。
- 状況は `/usage` で確認できる（キャッシュの当たり具合・ミスの原因が出る）。

### Codex（`codex exec` は毎回新しい会話）

- `codex exec` は呼ぶたびに新しい会話なので、**モデル・強度を毎回自由に指定でき、切り替えのペナルティはない**。
  ```
  codex exec -m <モデル> -c model_reasoning_effort=<強度> -s read-only -C . -o <出力> -
  ```
- 使えるモデル・強度はアカウントによる。現在確認できているのは `gpt-5.6-sol`（`docs/HANDOFF.md` 参照）。強度の例は low / medium / high / xhigh / max（モデルによって使える範囲が違う）。使えないモデルは 400 エラーになる。
- 同じ会話の続き（`codex exec resume --last`）には、モデル指定のオプションが資料に無い。続きでは前回と同じモデルのまま使い、**別のテーマ・別のモデルにしたいときは新しく `codex exec` を呼ぶ**。
- 目安（Claude Code が依頼ごとに決めて指定する）:
  - 段階 1 の通常の監査（A）: 既定のモデル、強度 medium〜high。
  - 段階 2・公開前ゲート・分析と提案（C）: 同じモデルで強度 high〜xhigh。
  - 軽い確認（動作確認など）: 強度 low。
- 設定ファイル（`~/.codex/config.toml`）の既定は変えず、毎回コマンドで指定する（利用者が既定を直すと決めたときを除く）。
- Codex を新しいバージョンに更新すると、使えるモデルが増える可能性がある（公式資料に `gpt-6.1-sol` の記載あり。ただし、あなたのアカウントで使えるかは未確認）。
